# Reporting customer history snapshots

The remaining seven financial APIs are still on the coordinated financial database. This change extends the staged Reporting core; it does not switch a production API, create a persistent Reporting database, or complete service isolation.

## Authoritative source

`CustomerHistoryExportService` is owned by FinancialOutbox infrastructure. With `ReportingSourceServer:Enabled`, authenticated operators can prepare a customer export under `/internal/v1/reporting-source/companies/{companyId}/customers/{customerId}/exports` and fetch the frozen export by ID. Prepare requires `ReportManage`, a company-scoped idempotency key and reason. Read requires `ReportRead`. The neutral `CustomerHistoryV1` contract contains customer identity/version, invoice reference/due dates, signed invoice/credit/debit journals, posted payments, refund/reversal cash adjustments, and dated allocation/release journals. V1 explicitly supports BDT, matching existing customer reports.

Preparation uses the existing command transaction and exclusive company financial fence. It validates the complete customer payment/correction graph and every posted invoice using the authoritative reconcilers, retains signed ledger tax amounts, and refuses missing posted versions. Pending/cancelled cash documents are excluded from output, while pending history still participates in reconciliation. Collection counts are bounded before reconciliation; oversized exports fail rather than dropping old opening movements. Complete output is limited to 10,000 rows and 8 MiB. It has no date filter: all captured history is needed for statement opening balances and historical ageing.

The existing immutable `platform.reporting_source_exports` stores the separate `customer-history-v1` scope, canonical JSON and SHA-256. Financial and customer export readers enforce their scope. Source exports, audit and command receipt commit together. Reading an old export after later financial posting returns its original history. No source migration, dispatch lease reset or event rewrite is needed.

## Independent consumer

`VerifiedCustomerHistory` validates the requested tenant/company/customer/export, coverage, exact count, canonical ordering, fingerprint, money precision, document signs, invoice/due dates, payment references, allocation/release graph and dated cash funding. It copies collections into immutable views. The pure `CustomerHistoryProjection` builds `[from, until)` statements with all prior opening movements and inclusive-as-of ageing. Credit balances, unknown due dates, exact overdue buckets, unapplied cash, refunds and allocation releases retain the existing report semantics. Tax is never recalculated.

`CustomerSnapshotService.Bootstrap` downloads through the delegated `ICustomerHistorySource`, verifies everything before opening the target write transaction, and enforces a 20-second deadline. The production HTTP adapter uses the same fixed trusted HTTPS origin, original bearer token and no-redirect/no-cookie policy as the financial export adapter. Known and streamed body lengths are bounded. A future host must bind that token to the actor from its authenticated principal.

The Reporting-owned migration `20261024153403_CustomerHistorySnapshots` adds `reporting.customer_snapshot_generations` and `reporting.customer_snapshot_audit`. Existing owned command receipts hold actor/customer/payload-bound results. Company advisory locks make concurrent bootstrap retries commit once; generation, audit and receipt are atomic. Same export/changed evidence conflicts. A committed retry works without the financial source. PostgreSQL triggers prohibit UPDATE/DELETE/TRUNCATE of generations and audit; the migration is forward-only. Composite audit foreign keys retain customer/company/tenant scope.

Reads select an explicit scoped generation ID, so they never silently choose another customer's snapshot or query financial SQL. Responses carry `SnapshotOnly=true`, `LiveCoverageVerified=false` and source capture time. No active customer live head or event watermark is implied. Runtime privileges for these tables should be SELECT/INSERT only, with migrations owned by a separate identity. Libraries perform no DDL during requests.

## Verification and remaining delivery

Tests cover dated statements, credit/debit/refund signs, allocations/releases, invalid rehashed references/money/coverage, restart/offline replay, concurrency, tenant/customer/permission isolation, append-only evidence and rollback when audit fails. The source parity test creates real invoice, credit/debit note, payment, allocation and refund through authenticated APIs, downloads the real export through the production HTTP adapter, migrates a separate disposable Reporting database and compares legacy/new statement and ageing results across three historical windows. It also checks frozen source history after a later receipt. Source tests cover empty complete history, read/manage permissions, export scope confusion and audit/receipt rollback.

Final verification on 24 October 2026: the complete 56-project Release build passed with zero warnings/errors. All **79 selected affected tests passed** (39 source/customer/payment API cases and 40 independent Reporting core/HTTP cases), including real separate-database customer parity. Both financial and Reporting EF models have no pending migration changes. Seven other test projects had no matching cases under the explicit filter; this is not a fresh full-suite or live broker verification. Temporary databases were removed and the test PostgreSQL cluster stopped. Logs use `artifacts/customer-history-*`, TRX results use `TestResults/customer-history-final`, and the source/test evidence manifest is under `artifacts/reporting-customer-history`.

The financial portion of generation-scoped inbox/deduplication/quarantine and atomic replay is subsequently delivered in [0030](0030-reporting-financial-generation-inbox.md), adding a third owned migration. Customer live coverage, a gap-proof catch-up boundary and freshness/checkpoint semantics, coordinated customer/financial promotion, and complete runtime route/operator coverage remain required before migration/provisioning/cutover. The financial source remains at 19 migrations. Runtime ownership remains five independent and seven coordinated APIs.
